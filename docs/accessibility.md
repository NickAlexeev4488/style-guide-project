# Доступность документации

Доступная документация должна быть понятна пользователям с разным уровнем подготовки и не должна требовать восприятия информации только одним способом.

## Понятный язык

Используйте короткие предложения и знакомые слова. Специальные термины объясняйте при первом появлении. Не объединяйте несколько самостоятельных действий в одном шаге.

Правильно:

1. Откройте файл `mkdocs.yml`.
2. Добавьте страницу в раздел `nav`.
3. Сохраните файл.

Неправильно:

> Откройте конфигурацию, внесите все необходимые изменения и проверьте результат.

## Заголовки

Заголовки должны образовывать последовательную иерархию. Не пропускайте уровни и не используйте заголовки только ради визуального выделения текста.

## Ссылки

Текст ссылки должен описывать её назначение.

Правильно:

```markdown
Ознакомьтесь с
rules.md
.
```

Неправильно:

```markdown
Нажмите
rules.md
.
```

## Изображения

Каждое значимое изображение должно иметь краткое и понятное альтернативное описание. Не используйте имя файла вместо описания.

```markdown
!
assets/images/build-success.png

```

Информация, необходимая для выполнения действия, должна быть продублирована текстом. Снимок экрана не заменяет инструкцию.

## Цвет

Не передавайте смысл только цветом. Ошибка, предупреждение или успешный результат должны иметь текстовое обозначение.

## Таблицы

Используйте понятные заголовки столбцов. Не создавайте таблицы только для визуального расположения текста. Сложную таблицу лучше разделить или заменить отдельными разделами.

## Код и команды

Для блока кода указывайте язык. Перед командой объясняйте её назначение, а после команды описывайте ожидаемый результат.

## Проверка доступности

Перед публикацией проверьте:

- логичность структуры заголовков;
- понятность текста ссылок;
- наличие описаний у изображений;
- возможность понять материал без различения цветов;
- читаемость списков и таблиц;
- наличие текстового пояснения для схем и снимков экрана.
